## 1. Продукт

«Стук» — диагностика неисправностей автомобиля по симптомам и звуку. Пользователь — встревоженный владелец машины БЕЗ технического бэкграунда: услышал стук/гул/визг, боится ехать в сервис вслепую.

Флоу: короткий опросник (дерево решений) → бесплатный предварительный вердикт → запись звука 15–30 сек → серверный анализ (DSP + мультимодальная LLM) → отчёт: вероятные причины с процентами, светофор срочности, «что сказать в сервисе».

Позиционирование: спокойный медицинский инструмент (референсы: Ada Health для анкеты, Shazam для записи, Yuka для вердикта). НЕ «гаражное» приложение, НЕ «AI-игрушка».

Продукт даёт вероятностную оценку, не диагноз. Дисклеймер обязателен в отчёте, на сайте и в описаниях.

## 4. Дизайн-система (единая для сайта и приложения)

Это ответ на требование «всё гармонично сочетается»: одни токены в двух реализациях (Tailwind config на сайте, ThemeData во Flutter). Ни один цвет/радиус/размер шрифта не задаётся вне токенов.

**Цвета:**

| Токен | Hex | Использование |
|---|---|---|
| `bg` | `#FFFFFF` | фон |
| `surface` | `#F5F7F9` | карточки, поля |
| `ink` | `#16232E` | основной текст (тёмный сине-серый, не чёрный) |
| `ink-soft` | `#5C6B78` | вторичный текст |
| `accent` | `#0E7C7B` | тил: кнопки, ссылки, прогресс, акценты |
| `accent-soft` | `#E2F1F0` | подложки акцента |
| `ok` | `#1B9E4B` | светофор: можно ехать |
| `warn` | `#D97E00` | светофор: в сервис на неделе |
| `stop` | `#D64545` | светофор: прекратить движение |

Жёсткое правило: `ok/warn/stop` используются ТОЛЬКО в светофоре срочности и маркерах опасности причин. Красный нигде больше не появляется (ошибки форм — `ink` + текст). Это делает светофор сигнатурным элементом продукта.

**Типографика:** Manrope (variable). Сайт — через `@fontsource-variable/manrope`, self-hosted; приложение — `google_fonts`. Роли: display 700 (заголовки, вердикт), body 400/500, данные и проценты — tabular-nums 600. Шкала сайта: 15/17/20/24/32/44. Flutter: 14/16/18/22/28.

**Форма:** радиус карточек 16, кнопок 14, полей 12. Отступы кратны 4 (базовая сетка 8). Тени почти нет: карточки = `surface` + 1px `#E7ECF0`. Минимальная высота тап-целей во Flutter — 56dp (юзер стоит на улице, солнце, одна рука).

**Иконки:** lucide (сайт) / Material Symbols rounded (Flutter). Линейные, вес одинаковый. Без эмодзи в UI.

**Сигнатура:** плашка вердикта-светофора — крупный цветной блок с коротким глаголом («Можно ехать» / «В сервис на неделе» / «Остановись») + одна строка причины. Один и тот же компонент визуально на сайте (в дереве и таблицах причин) и в приложении (в отчёте).

**Запреты:** тёмная «гаражная» тема, карбон, неон, циферблаты; фиолетовые градиенты и ✨; слово «AI» как украшение в UI; кремовый фон с терракотовым акцентом и прочие шаблонные AI-эстетики. Стиль — светлый, врачебный, сдержанный. Motion: только пульсация кнопки записи, плавный прогресс анализа и появление отчёта; `prefers-reduced-motion` уважать.

**Копирайтинг UI:** простой разговорный русский, глаголы действия («Записать звук», не «Начать аудиофиксацию»), обращение на «ты» недопустимо — нейтральные формулировки без обращения («Поднесите телефон…» → лучше безлично: «Телефон ближе к источнику звука»). Ошибки объясняют, что делать дальше, без извинений и без вины пользователя.

## 5. shared/tree.json

**Схема:**

```json
{
  "version": 1,
  "root": "q_when",
  "nodes": {
    "q_when": {
      "type": "question",
      "text": "Когда слышен звук?",
      "options": [
        { "id": "o1", "label": "На месте, при работающем двигателе", "next": "q_engine_char" },
        { "id": "o2", "label": "Только в движении", "next": "q_move_speed" }
      ]
    },
    "leaf_wheel_bearing": {
      "type": "leaf",
      "top_cause": "Ступичный подшипник",
      "alt_causes": ["Шум резины", "Подвесной подшипник"],
      "urgency": "warn",
      "explanation": "2–3 предложения простым языком: что это и почему так звучит.",
      "advice": "Что проверить самому + чего не делать.",
      "site_slug": "gul-pri-dvizhenii"
    }
  }
}
```

**Требования к содержанию (это доменное ядро продукта, делай тщательно):**
- Глубина 3–6 вопросов, варианты 2–4, формулировки бытовые («когда крутите руль», не «при вращении рулевого колеса»). Один вопрос — одна ось.
- Обязательные диагностические оси, вокруг которых строится дерево:
  1. Звук зависит от оборотов двигателя или от скорости движения (проверка «газануть на нейтрали»).
  2. Только на холодную / всегда.
  3. Появляется при торможении / при повороте / на неровностях / при разгоне.
  4. Характер: стук, тиканье, гул, визг/свист, скрежет, щелчки, хлопки.
  5. Локализация: спереди / сзади / из-под капота / из-под днища.
- Минимум 16 листьев. Обязательно покрыть: клапанный стук (тиканье), цепь/натяжитель ГРМ на холодную, визг ремня, помпа, ролики, ступичный подшипник (в т.ч. связь с поворотом: гул сильнее при повороте налево → нагружена правая ступица), ШРУС (щелчки в повороте), стойки стабилизатора и сайлентблоки (стук на мелких неровностях), опоры двигателя, тормоза (скрип/скрежет, индикатор износа), выхлоп (хлопки, звон теплозащитного экрана), детонация (звон при разгоне под нагрузкой), гидрокомпенсаторы.
- Каждый лист: честный `top_cause` без притянутой уверенности, `urgency` по здравому смыслу (скрежет тормозов = `stop`; звон экрана = `ok`), `site_slug` из списка §9.
- `validate-tree.mjs`: все `next` существуют, нет недостижимых узлов, нет циклов, у каждого листа заполнены все поля, каждый `site_slug` из списка §9. Запуск: `node shared/validate-tree.mjs` — падает с внятной ошибкой.

## 6. Backend (Go 1.22+)

Стек: chi, стандартная библиотека везде, где возможно. Логи — slog (JSON). Без БД: состояние — in-memory с периодическим сбросом в `data/state.json`.

**Эндпоинты:**
- `GET /healthz` → 200.
- `GET /api/v1/version` → `{ "latest_version": "1.0.0", "apk_url": "<PUBLIC_SITE_URL>/app/stuk.apk" }` (значения из конфига).
- `POST /api/v1/report` — основной. `multipart/form-data`: поле `audio` (WAV) + поле `meta` (JSON):

```json
{
  "device_id": "uuid",
  "car": { "make": "Skoda", "model": "Rapid", "year": 2014, "mileage_km": 150000 },
  "answers": [ { "question_id": "q_when", "option_id": "o2", "question_text": "...", "option_label": "..." } ],
  "leaf_id": "leaf_wheel_bearing"
}
```

**Пайплайн `/report`:**
1. Валидация: `MaxBytesReader` 6 MB; WAV PCM16 mono 16000 Hz, длительность 5–35 сек — иначе 422 с человекочитаемой причиной (клиент гарантирует формат, но сервер не доверяет).
2. Лимит: `DAILY_FREE_LIMIT` (default 3) отчётов на device_id в сутки → 429 c текстом «Лимит на сегодня исчерпан, возвращайтесь завтра». Плюс rate limit 10 req/min на IP.
3. DSP (§6.1) → структура фич.
4. Gemini (§6.2) → структурированный отчёт.
5. Ответ: JSON отчёта (схема в §6.2) + `dsp_summary` для отладки. Общий таймаут 75 сек.

### 6.1 Пакет `dsp`

Чистая математика, без ML. FFT: либо `github.com/mjibson/go-dsp/fft`, либо собственный radix-2 с тестами — выбери сам, что надёжнее соберётся.

Вычислить и вернуть с оценкой уверенности (`low/med/high`) каждую фичу:
- `duration_sec`, `rms_db`, грубая оценка SNR (тишина vs сигнал по перцентилям огибающей).
- Спектральный центроид; топ-3 спектральных пика с prominence → флаг «тональный звук» (визг ремня/подшипника) vs «широкополосный».
- Огибающая (rectify + lowpass) → детект ударных событий → частота повторения ударов `hit_hz` через автокорреляцию огибающей.
- Оценка оборотов: полосовая энергия 30–300 Гц → фундаментальная частота вспышек `fire_hz` через автокорреляцию; для 4-тактного 4-цилиндрового RPM = fire_hz × 30. Если пика нет — `rpm: unknown`.
- Если есть и `hit_hz`, и обороты: `ratio = hit_hz / rev_hz` + ближайшая интерпретация: ~0.5 → распредвал/клапаны; ~1.0 → коленвал/шатун; ~2.0 → частота вспышек/выхлоп. Обязательно с оговоркой уверенности.

Юнит-тесты обязательны, на синтетике: (а) синус 100 Гц → центроид и пик корректны; (б) гребёнка импульсов 20 Гц поверх шума → `hit_hz ≈ 20`; (в) тишина → все фичи `low`/unknown. Тестовый WAV-генератор положи в `backend/internal/dsp/testdata_gen.go` — он же пригодится для интеграционного curl-теста.

Принцип: DSP не ставит диагноз. Его выводы уходят в LLM как подсказки с явной пометкой надёжности.

### 6.2 Gemini

REST `v1beta generateContent`, модель — константа конфига `GEMINI_MODEL`, default `gemini-2.5-flash` (в README пометить: проверить актуальное имя flash-модели на момент запуска). Аудио — `inline_data` base64 `audio/wav`. Температура 0.2. Использовать structured output (`response_mime_type: application/json` + `response_schema`).

**Схема ответа (она же схема отчёта для клиента):**

```json
{
  "causes": [ { "title": "", "probability_pct": 0, "why": "", "check_yourself": "" } ],
  "urgency": "ok|warn|stop",
  "urgency_reason": "",
  "mechanic_brief": ["3–5 пунктов: что сказать в сервисе"],
  "mechanic_questions": ["вопросы, которые задаст механик"],
  "red_flags": ["при каких признаках остановиться немедленно"],
  "disclaimer": ""
}
```

**Системный промт Gemini** (константа в коде, на русском) должен включать: роль механика-диагноста с 20-летним опытом; входные данные (марка/модель/год/пробег, ответы анкеты, DSP-фичи с уровнями уверенности, само аудио); правила: 2–4 причины, вероятности честные и в сумме ≤ 100; анкета — главный сигнал, аудио и DSP — уточняющие; если аудио неинформативно (низкий SNR) — прямо сказать это и опереться на анкету; учитывать типовые болячки конкретной модели и возраста/пробега; никаких выдуманных уверенностей и запугивания; язык простой, термины расшифровывать в скобках; `urgency` консервативно: сомнение между warn и stop → stop только при реальных признаках опасности (тормоза, руль, стук из глубины двигателя под нагрузкой).

Ошибки Gemini (5xx, таймаут) → 502 с текстом «Не получилось проанализировать, попробуйте ещё раз» + retry-подсказка клиенту.

## 7. Приложение (Flutter, только Android)

**Экраны и флоу:**

1. **Первый запуск — машина:** марка (текст с подсказками из короткого локального списка популярных марок), модель (текст), год (picker 1990–2026), пробег (число, км). Сохранить в prefs; генерируется `device_id` (uuid). Редактирование — в настройках.
2. **Главный:** большая кнопка «Диагностировать», ниже — история отчётов (локально: JSON-файлы через path_provider; карточка = дата, машина, вердикт-светофор), ссылка «Как это работает».
3. **Опросник:** один вопрос на экран, варианты — крупные карточки (min 56dp), прогресс-бар сверху, «назад» работает. Данные — из tree.json.
4. **Предварительный вердикт (лист дерева):** плашка-светофор + `top_cause` + `explanation` + `advice`. CTA: «Уточнить по звуку — точный отчёт» с подписью «Пока бесплатно, до 3 отчётов в день». Кнопка «Достаточно» → сохранить как краткий отчёт в историю.
5. **Запись:** инструкция до записи (двигатель заведён; телефон ближе к источнику; 15–30 сек; если звук зависит от газа — плавно перегазовать во время записи; не разговаривать). Огромная круглая кнопка с мягкой пульсацией, live-волна амплитуды, таймер, автостоп на 30 сек. После — прослушать / перезаписать / отправить. Запись: WAV PCM16, 16000 Hz, mono (пакет `record`: encoder pcm16bits). Runtime-разрешение RECORD_AUDIO с объясняющим экраном до системного диалога; отказ — экран с объяснением и кнопкой в настройки.
6. **Анализ:** этапы со сменой статусов («Слушаю запись…» → «Считаю спектр…» → «Сопоставляю с симптомами…»), реальное ожидание ответа API до 75 сек. Ошибки сети/сервера — человеческий текст + «Повторить» (аудио не перезаписывать, слать то же).
7. **Отчёт:** сверху плашка-светофор (цвет + глагол + `urgency_reason`); причины списком: полоска процента (tabular-nums), title, разворачиваемые «Почему» и «Проверить самому»; блоки «Скажите в сервисе» (нумерованный), «Вопросы механика», «Когда остановиться немедленно» (маркер `stop`-цветом); дисклеймер мелким. Кнопка «Поделиться» → рендер шеримой карточки (RepaintBoundary → PNG): логотип «Стук», машина, светофор, топ-3 причины с процентами, подпись «stuk — диагностика по звуку» → share_plus. Карточка должна выглядеть как результат прибора, а не скриншот текста.
8. **Настройки:** машина, версия приложения, «Проверить обновления» (GET /api/v1/version → если новее, кнопка на скачивание через url_launcher), ссылки на сайт и политику.

`API_BASE_URL` — через `--dart-define`, дефолт `https://api.example.kz` (README: заменить). Иконка приложения: фон `accent`, белая упрощённая звуковая волна с одним «выбросом»-стуком; сгенерировать через `flutter_launcher_icons`. ### 8.1 Раздача APK

`site/public/app/stuk.apk` + `site/public/app/version.json` (`{"version":"1.0.0","size_mb":..,"updated":"YYYY-MM-DD"}`). Кнопка «Скачать для Android» показывает версию и размер (fetch version.json). Рядом — свёрнутая инструкция установки: скачать → открыть файл → разрешить установку из этого источника → установить; строка «Когда приложение появится в Google Play, эта страница обновится». `scripts/publish-apk.sh`: копирует tree.json в ассеты → `flutter build apk --release --dart-define=API_BASE_URL=...` → кладёт APK и version.json в `site/public/app/`.

### 8.2 Шаблон симптом-страницы

- H1 = поисковый запрос (напр. «Стук в двигателе на холодную»).
- Уникальный текст 500–800 слов, структура: что это может быть (абзац) → таблица «Причина / Насколько вероятно / Опасность» (опасность — мини-светофор §4) → «Можно ли ехать» → «Что проверить самому» (без разборки, безопасные проверки) → как поможет приложение (1 абзац, без давления).
- Интерактивное дерево — React-остров `client:visible`: тот же `shared/tree.json` (импорт на этапе билда), проп `startNode` — страница стартует с релевантной ветки, а не с корня. Финал ветки: плашка-светофор + top_cause + CTA «Полный отчёт по звуку — в приложении» → якорь на блок APK.
- SEO: уникальные title/description, canonical, OG; Schema.org `FAQPage` (3 вопроса из текста страницы). На главной — `SoftwareApplication`.

**Требования к текстам:** пиши сам, фактологически аккуратно (уровень: не стыдно показать механику), без штампов («в современном мире», «давайте разберёмся»), без обещаний точности, тон — спокойный эксперт. Причины и их типичность должны согласовываться с деревом решений — не противоречить `tree.json`.
